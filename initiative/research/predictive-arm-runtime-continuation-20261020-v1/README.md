# Runtime-only per-arm contingency — prepared, never launched

This is a conditional operational continuation for a **fully accepted combined B/C/C0 qualification**, followed by an original owner's runtime-projection rejection before any arm compilation or public push. It does not accept a partial/failed qualification, modify the nine-hour threshold, choose epochs or use scores. The healthy HTTP deployment owner remains unchanged.

`evaluate()` first invokes the exact original serving qualification validator for all three candidates. Any invalid source, learned weights, precision, memory or measurement stops globally. Only the original policy's exact nine-hour projection-excess error can reject one role while evaluating the others. Complete measurements and rejection reasons remain in the resulting record. Eligible roles retain their B/C/C0 order.

The original rule remains: approximately 1,300 studies, the slowest complete observed case divided across two lanes, 600 seconds startup and 1,800 seconds safety, within 32,400 seconds. Qualification is still the original 1,200-second combined run; the public watchdog is still 600 seconds. No extra probe, Dataset, model, qualification, budget reset or deletion credit is introduced. Rejected roles conservatively retain their public-execution reservation.

## Required actual boundary

After the original owner has actually stopped, `admit_failure()` checks:

- Its exact PID/source and original decision-file bytes; a retained `ValueError` terminal with no automatic retry and the PID absent.
- The original prepared three-final bundle, exact qualification push and matching authenticated `COMPLETE` result, plus the full accepted qualification receipt.
- No local arm intent/result, entry or completed all-arm runtime decision.
- A fresh, separately collected original-root/ledger observation showing no arm compilation, canonical row, push or submission and no account claim.
- At least one reproducible runtime-only rejection under the original policy.

`read_boundary(root, ledger)` is the small read-only collection function for the existing owning-node management environment. It reads original JSON receipts and opens SQLite with `mode=ro` and `query_only`; it refuses a claim or transient ledger sidecar. It makes no API calls, reads no credentials, allocates no GPU, and writes nothing. Its output must be collected within 180 seconds of admission. Any prior/uncertain arm action is outside this contingency and requires its own read-only reconciliation.

## Concrete integration

The parent must freeze this source and any adapter before invoking it. Historical numerical source `44cc559e…`, canonical account owner `8fd43b98…`, current HTTP placement source and existing final/export receipts stay bound.

1. Collect the actual read-only boundary, exact stopped-owner receipts and original prepared candidates. Load the serving validator and `runtime_plan`/policy from their existing frozen sources; call `admit_failure(...)`. No admission is fabricated during preparation.
2. Reuse the original portable deployment source and existing HTTP adaptations. Apply `derive_deployment_source(source)` before constructing its module. This changes only three exact anchors: the new local journal, attribution to the actual stopped owner, and the final `PortableDeployment().run()` call.
3. Inject `runtime_admission=actual_admission` and `continue_runtime=continue_qualified` into that module. Its original `PortableDeployment` class, source-bound `config`, `observe`, compiler, allowance, quota, lock, push and submit phases are unchanged. The existing HTTP path adaptations continue reading the original final/return receipts, not the new journal.
4. Explicitly run the derived adapter once. It uses `artifacts/predictive-arm-runtime-continuation-20261020-v1`; any existing continuation intent refuses another run. `continue_qualified()` performs only `compile → push → public status → submit → hidden outcome` for eligible roles. The original October 22 noon UTC launch cutoff and original outcome deadline remain active.

The callable tail can also be supplied a separately constructed exact original portable owner directly. It requires a distinct journal, the unchanged canonical pin and decision, and fresh admission. It never reconstructs or silently resumes an uncertain mutation.

Prebinding this into a replacement owner **before** qualification would require a separate explicit idle-owner handoff and reviewed owner-source change. That is unnecessary while the original owner is healthy. The current implementation is ready as a narrow post-failure building block; it is not a launched watchdog or an authorization to replace the live owner.

Local tests exercise the actual frozen runtime policy and serving qualification validator using synthetic timings: an over-limit middle arm cannot block a valid later arm; invalid qualification and unrelated errors still stop globally; prior local/remote activity is refused; and the executable tail uses only eligible original account phases once. These tests are not trained-model or Kaggle evidence.
